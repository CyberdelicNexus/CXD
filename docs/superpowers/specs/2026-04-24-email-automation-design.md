# Email Automation — Trial Lifecycle and Payment Dunning

**Date:** 2026-04-24
**Scope:** Phase 1. Focused on the Pro trial lifecycle and payment-failure dunning. Other UX email touchpoints (inactive user, canvas comments, credit-low warnings, etc.) are explicitly out of scope and left for a Phase 2 spec.

## Goal

Send the right email to the right user at the right moment across the Pro subscription lifecycle, driven by a mix of Stripe webhook events and a daily Vercel Cron job. Simultaneously fix the missing `customer.subscription.updated` webhook handler so the Supabase `subscriptions.status` column stays in sync with Stripe's source of truth (currently stuck at `trialing` even after Stripe auto-converts to `active`).

## Non-goals

- Welcome/onboarding emails beyond the existing `welcome.tsx`
- Inactive user re-engagement, feature announcements, comment notifications
- Credit-low warnings
- Custom Stripe dunning retry logic (we keep Stripe's existing Smart Retry: 4 attempts over 1 week)
- Manual email broadcasts / campaigns

## Email cadence

Five new templates plus one critical webhook fix.

| # | When                        | Trigger                                                | Template                |
|---|-----------------------------|--------------------------------------------------------|-------------------------|
| 1 | Trial day 1                 | Vercel Cron                                            | `trial-day-1`           |
| 2 | Trial ends in ~3 days       | Stripe webhook `customer.subscription.trial_will_end`  | `trial-ending-soon`     |
| 3 | Trial converted to paid     | Stripe webhook `invoice.paid` (first post-trial)       | `trial-converted`       |
| 4 | Payment failed (day 0)      | Stripe webhook `invoice.payment_failed`                | `payment-failed`        |
| 5 | Payment still failing (day 5) | Vercel Cron                                          | `payment-final-warning` |

Stripe's existing Smart Retry (4 attempts over 1 week, cancel on all failures) is not changed. If all retries fail at day 7, Stripe fires `customer.subscription.deleted` which already triggers the existing `subscription-cancelled` email.

## Template copy direction

All templates match the brand voice and visual style of existing `emails/subscription-confirmed.tsx`: calm, direct, no em-dashes, single clear CTA, plain-text fallback auto-generated by React Email.

### 1. `trial-day-1`
- Subject: `Your Pro trial is live — let's get started`
- Body: 3 getting-started tips (create your first canvas, try the hypercube, invite a collaborator), link to dashboard. Soft-sell: "Your trial runs through [date]."

### 2. `trial-ending-soon`
- Subject: `Your Pro trial ends on [date]`
- Body: billing-date reminder, confirms the card Stripe has on file (last 4 digits), provides manage-billing link. Tone: informational, not anxious.

### 3. `trial-converted`
- Subject: `Welcome to Pro`
- Body: first charge succeeded, credit allowance refreshed, next billing date, receipt link.

### 4. `payment-failed`
- Subject: `We couldn't charge your card`
- Body: soft tone, mentions retry attempts, CTA to update payment method. Avoid fear language; users should feel it's a routine issue.

### 5. `payment-final-warning`
- Subject: `Last chance to restore Pro access`
- Body: firm tone, explicit consequence (access drops to Free tomorrow), prominent CTA to update card.

## Architecture

### Event-driven emails — extend the Stripe webhook

File: [src/app/api/webhooks/stripe/route.ts](CXD/src/app/api/webhooks/stripe/route.ts)

Four new `switch` cases:

- **`customer.subscription.trial_will_end`** — Stripe fires this ~3 days before `trial_end`. Look up the user's subscription row, render `trial-ending-soon`, send via Resend.
- **`invoice.paid`** — Fires for every successful invoice. We only send the `trial-converted` email the *first* time after the trial ended (check `billing_reason === 'subscription_cycle'` AND the previous `status` on the subscription row was `trialing`). Subsequent monthly renewals do NOT send an email (silent charge).
- **`invoice.payment_failed`** — Render `payment-failed`, send. Also update Supabase `subscriptions.status` to `past_due`. Log the `invoice.id` in the `email_log` table so the cron job can key off it.
- **`customer.subscription.updated`** — Sync Supabase's `plan_id`, `status`, `current_period_*`, `trial_*`, `cancel_at_period_end`, `canceled_at` with the Stripe subscription object. No email — this handler exists only to keep our DB in sync and is the fix for the trial→paid auto-flip bug.

### Time-driven emails — new Vercel Cron route

File to create: `src/app/api/cron/email-scheduler/route.ts`
Schedule: `0 14 * * *` (daily 14:00 UTC ≈ 10am ET / 7am PT — inside business hours for both coasts and Europe).
Config: `vercel.json` adds a `crons` array entry.
Auth: the route checks `Authorization: Bearer ${process.env.CRON_SECRET}`; returns 401 if missing/wrong. Vercel Cron supplies this header automatically when `CRON_SECRET` env var is set.

The cron job runs two scans, both guarded by `email_log` idempotency:

1. **Trial day 1 scan** — fetch `subscriptions` where `status='trialing'` AND `trial_start` was between 24–48 hours ago. Exclude any user with an existing `email_log` row for `email_kind='trial-day-1'`. Send the email, insert into `email_log`.

2. **Payment failed day 5 scan** — fetch `subscriptions` where `status='past_due'` AND there exists an `email_log` row with `email_kind='payment-failed'` whose `sent_at` was between 4.5–5.5 days ago. Exclude users with an existing `email_log` row for `email_kind='payment-final-warning'`. Send the email, insert into `email_log`.

The 1-hour windows (`24–48 hours`, `4.5–5.5 days`) protect against missed days if the cron fails once.

### Idempotency table

New Supabase table `email_log`:

```sql
create table public.email_log (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  email_kind text not null,
  sent_at timestamptz not null default now(),
  stripe_event_id text,
  metadata jsonb
);

create index email_log_user_kind_idx on public.email_log(user_id, email_kind);
create index email_log_stripe_event_idx on public.email_log(stripe_event_id) where stripe_event_id is not null;
```

RLS: service-role only. No client reads.

Idempotency is checked by `(user_id, email_kind)` for the scheduled emails, and by `stripe_event_id` for the webhook-triggered ones.

### Environment variables

- `CRON_SECRET` — new, Sensitive. Generate with `openssl rand -hex 32`. Used for Authorization header verification on the cron endpoint.
- `RESEND_API_KEY` — existing, Sensitive (already).
- `RESEND_FROM_EMAIL` — existing, optional.

## Stripe dashboard changes the user needs to apply

Only one toggle:

- **Settings → Billing → Subscriptions and emails → Manage invoices sent to customers → Send reminders if a recurring invoice hasn't been paid** — turn this OFF. It overlaps with our `payment-failed` template and would cause duplicate communication. The other invoice toggle ("Send finalized invoices and credit notes") stays ON for tax/legal compliance.

All other Stripe settings audited and correct: generic customer emails off, Smart Retry set to 4 attempts over 1 week with cancel-on-failure, Business customer emails for successful payments / refunds off.

## Data flow for each email

### Trial day 1 (cron)
```
Cron fires → scan subscriptions (status=trialing, 24–48h since trial_start)
→ for each, check email_log for (user_id, 'trial-day-1') absent
→ render trial-day-1 template → sendEmail → insert email_log
```

### Trial ending soon (webhook)
```
Stripe → customer.subscription.trial_will_end
→ look up user_id from subscription
→ check email_log for (stripe_event_id=event.id) absent
→ render trial-ending-soon → sendEmail → insert email_log
```

### Trial converted (webhook)
```
Stripe → invoice.paid → check invoice.billing_reason === 'subscription_cycle'
→ look up subscription row; if previous status was 'trialing'
→ check email_log for (stripe_event_id=event.id) absent
→ render trial-converted → sendEmail → insert email_log
→ update subscription status to 'active' (also done by subscription.updated)
```

### Payment failed (webhook)
```
Stripe → invoice.payment_failed
→ look up user_id
→ check email_log for (stripe_event_id=event.id) absent
→ render payment-failed → sendEmail → insert email_log
→ update subscription status to 'past_due'
```

### Payment final warning (cron)
```
Cron fires → scan subscriptions (status=past_due) joined with email_log
→ for each past_due user with a payment-failed log 4.5–5.5 days ago
  AND no payment-final-warning log
→ render payment-final-warning → sendEmail → insert email_log
```

### Subscription status sync (webhook, no email)
```
Stripe → customer.subscription.updated
→ sync plan_id, status, current_period_*, trial_*, cancel_at_period_end, canceled_at
→ no email
```

## Error handling

- Webhook email failures are caught and logged (existing pattern in the webhook). They do NOT fail the webhook response — Stripe would retry the event and we'd risk double-sending.
- Cron email failures per-user are caught, logged, and the loop continues. The `email_log` insert happens AFTER successful send so failed sends can be retried on the next cron run.
- Resend API outages: Resend client raises; we catch and log. A brief outage results in a 1-day email delay (next cron run). Acceptable for Phase 1.

## Testing

- **Webhooks:** use the Stripe CLI (`stripe trigger customer.subscription.trial_will_end` etc.) to fire events against local `stripe listen --forward-to localhost:3000/api/webhooks/stripe`. Verify each handler sends via Resend's test mode (Resend logs every send in the dashboard; OK even without real delivery).
- **Cron:** call the endpoint manually with `curl -H "Authorization: Bearer $CRON_SECRET" https://canvas.cyberdelic.design/api/cron/email-scheduler` in production, or locally with the dev server. Seed test data in Supabase with fake `trial_start` timestamps matching the 24–48h window.
- **Idempotency:** call the cron twice, verify only one send logged per user.
- **Full-flow dry run:** create a Pro trial in Stripe test mode with a pre-declining test card (`4000000000000341`) and let the retry cycle play out. Verify emails fire at each expected moment.
