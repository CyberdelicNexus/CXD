<objective>
Diagnose and fix why collaborator-originated Yjs changes are not persisted to Supabase, so that BOTH owner and collaborator changes survive page reload.

Purpose: This is the #1 bug blocking soft launch. Users in a live workshop are losing collaborator work on reload. The root cause is in the persistence layer -- the Yjs CRDT syncs changes between peers in real-time (so collaborators SEE each other's changes), but when ALL peers close the page, only the owner's persistence save succeeds because the SupabasePersistence class does a bare Supabase `.update()` that likely fails RLS for non-owners.

Output: A fixed `SupabasePersistence` that reliably saves for both owners and collaborators.
</objective>

1. `src/lib/yjs/supabase-persistence.ts` — the `save()` method does `supabase.from('cxd_projects').update({ yjs_state, updated_at }).eq('id', projectId)`. 2. `src/lib/supabase-projects.ts` — the `saveProject()` function (JSON project_data save) explicitly checks if the user is a collaborator via the `canvas_collaborators` table before saving. It uses the same `.update().eq('id', projectId)` pattern. The comments in this file (lines 186-191) state that UPDATE was chosen over UPSERT specifically because "UPSERT fails for collaborators." This confirms the RLS UPDATE policy DOES allow collaborators — otherwise `saveProject` wouldn't work either.

3. Check the Supabase RLS policies: Since `saveProject` (JSON save) works for collaborators but `SupabasePersistence.save()` (binary yjs_state save) might not, the issue is likely one of:
   - (a) The `SupabasePersistence.save()` error is being silently swallowed (it logs but doesn't retry or alert)
   - (b) The `SupabasePersistence` is only constructed for the OWNER, not for collaborators
   - (c) The `yjs_state` column save is succeeding but getting OVERWRITTEN by the owner's save (race condition — last writer wins on the binary blob)

4. Read `src/contexts/yjs-project-context.tsx` — SupabasePersistence is created in the `YjsProjectProvider` useEffect. This runs for EVERY user (owner and collaborator). So (b) is ruled out.

5. The REAL root cause is likely (c): a race condition. Both owner and collaborator have `SupabasePersistence` instances, both listen to `doc.on('update')` and schedule debounced saves. When saves race, last-writer-wins causes data loss.

6. Read `src/hooks/use-project-sync.ts` — check `flushPendingSave()` which creates a transient `SupabasePersistence` instance.

**After diagnosis, implement the fix:**

**Part A: Make SupabasePersistence.save() use read-merge-write instead of blind overwrite**

The current `save()` calls `Y.encodeStateAsUpdate(this.doc)` which produces the FULL document state. When two clients race, last-writer-wins causes data loss.

Change the save strategy to a merge-safe approach:
- In `save()`, load the current `yjs_state` from Supabase FIRST
- Apply it to a temporary Y.Doc
- Merge the local doc's state into the temp doc
- Encode the merged result and save THAT back
- This ensures no collaborator changes are lost even if saves race

Implementation:
```typescript
async save(): Promise<void> {
  if (this.destroyed || this.isSaving) return;
  this.isSaving = true;
  try {
    const supabase = createClient();

    // 1. Load current persisted state
    const { data } = await supabase
      .from('cxd_projects')
      .select('yjs_state')
      .eq('id', this.projectId)
      .single();

    // 2. Create a merge doc
    const mergeDoc = new Y.Doc();

    // 3. Apply persisted state first (if any)
    if (data?.yjs_state) {
      const persisted = Uint8Array.from(atob(data.yjs_state), c => c.charCodeAt(0));
      Y.applyUpdate(mergeDoc, persisted);
    }

    // 4. Apply our local state on top (Yjs CRDT merge — never loses data)
    const localState = Y.encodeStateAsUpdate(this.doc);
    Y.applyUpdate(mergeDoc, localState);

    // 5. Encode the merged result
    const merged = Y.encodeStateAsUpdate(mergeDoc);
    mergeDoc.destroy();

    // 6. Save the merged state
    let binary = '';
    for (let i = 0; i < merged.length; i++) {
      binary += String.fromCharCode(merged[i]);
    }
    const base64 = btoa(binary);

    const { error } = await supabase
      .from('cxd_projects')
      .update({
        yjs_state: base64,
        updated_at: new Date().toISOString(),
      })
      .eq('id', this.projectId);

    if (error) {
      console.error('[SupabasePersistence] Failed to save Y.Doc state:', error);
    }
  } catch (err) {
    console.error('[SupabasePersistence] Save error:', err);
  } finally {
    this.isSaving = false;
  }
}
```

Fix the `flushPendingSave()` function in `src/hooks/use-project-sync.ts`. The current code creates a transient `SupabasePersistence` instance, calls `persist.save()` WITHOUT await, then immediately calls `persist.destroy()`. This means `destroy()` sets `destroyed=true` while `save()` is still in-flight, causing the save to be silently skipped.

The fix: `await persist.save()` before calling `persist.destroy()`. After Task 1's fix to `destroy()` ordering, `destroy()` itself will also call `save()` — but the transient instance pattern still needs the explicit await because the caller expects the save to be complete before navigation occurs.

Change this:
```typescript
const persist = new SupabasePersistence(yDoc, currentProjectId);
await persist.save();
persist.destroy();
```

Specifically:
1. Find the `flushPendingSave()` function
2. Ensure `persist.save()` is awaited
3. Ensure `persist.destroy()` is called AFTER the save completes
4. If `persist.destroy()` was not previously awaited, await it too (since after Task 1, destroy() calls save() internally which is async)

Note: After Task 1's destroy() fix, calling `persist.destroy()` after `await persist.save()` will attempt a second save inside destroy(). To avoid the double save, either:
- (a) Call `await persist.save()` then set `persist.destroyed = true` manually (if the field is public), OR
- (b) Just call `await persist.destroy()` alone (since destroy() now saves first), OR
- (c) Keep `await persist.save()` then `persist.destroy()` — the second save in destroy() will be a no-op because `isSaving` will short-circuit or the state hasn't changed

Option (c) is safest and simplest. The read-merge-write in the second save will produce an identical result (idempotent), so it's harmless.
