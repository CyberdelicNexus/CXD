<objective>
Diagnose and fix why collaborator-originated Yjs changes are not persisted to Supabase, so that BOTH owner and collaborator changes survive page reload.

Purpose: This is the #1 bug blocking soft launch. Users in a live workshop are losing collaborator work on reload. The root cause is in the persistence layer -- the Yjs CRDT syncs changes between peers in real-time (so collaborators SEE each other's changes), but when ALL peers close the page, only the owner's persistence save succeeds because the SupabasePersistence class does a bare Supabase `.update()` that likely fails RLS for non-owners.

Output: A fixed `SupabasePersistence` that reliably saves for both owners and collaborators.
</objective>

   - (b) The `SupabasePersistence` is only constructed for the OWNER, not for collaborators

4. Read `src/contexts/yjs-project-context.tsx` — SupabasePersistence is created in the `YjsProjectProvider` useEffect. This runs for EVERY user (owner and collaborator). So (b) is ruled out.

5. The REAL root cause is likely (c): a race condition. Here's why:
   - Both owner and collaborator have a `SupabasePersistence` instance
   - Both listen to `doc.on('update')` and schedule debounced saves (2s)
   - When a collaborator makes a change, their Y.Doc updates, and their `SupabasePersistence` saves the full Y.Doc state

   - If the owner's save happens AFTER the collaborator's but the owner's Y.Doc hasn't yet received the update (due to network latency), the owner's save overwrites the collaborator's state with an older version
   - On reload, the yjs_state in DB is the owner's older version, missing the collaborator's change

6. Additionally, check `src/hooks/use-project-sync.ts` — `useProjectSync()` saves `project_data` (JSON) with a 1s debounce. The `project_data` JSON is a SEPARATE save path from `yjs_state`. On reload, which one wins? Check `yjs-project-context.tsx` lines 105-128 — the load order is: IndexedDB first, then Supabase `yjs_state`, then fallback to project_data JSON. So `yjs_state` takes priority. If `yjs_state` is stale (owner overwrote), the collaborator's JSON save is ignored.

Fix the persistence layer based on the diagnosis. The fix has two parts:

**Part A: Make SupabasePersistence.save() use Yjs state vectors instead of full state overwrites**

The current `save()` calls `Y.encodeStateAsUpdate(this.doc)` which produces the FULL document state. When two clients race, last-writer-wins causes data loss.

The fix: Change the save strategy so that instead of overwriting `yjs_state` with the full state, we use a merge-safe approach:

Option 1 (RECOMMENDED — simplest, works within current architecture):
- In `save()`, load the current `yjs_state` from Supabase FIRST
- Apply it to a temporary Y.Doc
- Merge the local doc's state into the temp doc
- Encode the merged result and save THAT back
- This ensures no collaborator changes are lost even if saves race

Implementation for Option 1:
```typescript
async save(): Promise<void> {
  if (this.destroyed || this.isSaving) return;
  this.isSaving = true;
  try {
    const supabase = createClient();

    // 1. Load current persisted state
    const { data } = await supabase
      .from('cxd_projects')
      .select('yjs_state')
      .eq('id', this.projectId)
      .single();

    // 2. Create a merge doc
    const mergeDoc = new Y.Doc();

    // 3. Apply persisted state first (if any)
    if (data?.yjs_state) {
      const persisted = Uint8Array.from(atob(data.yjs_state), c => c.charCodeAt(0));
      Y.applyUpdate(mergeDoc, persisted);
    }

    // 4. Apply our local state on top (Yjs CRDT merge — never loses data)
    const localState = Y.encodeStateAsUpdate(this.doc);
    Y.applyUpdate(mergeDoc, localState);

    // 5. Encode the merged result
    const merged = Y.encodeStateAsUpdate(mergeDoc);
    mergeDoc.destroy();

    // 6. Save the merged state
    let binary = '';
    for (let i = 0; i < merged.length; i++) {
      binary += String.fromCharCode(merged[i]);
    }
    const base64 = btoa(binary);

    const { error } = await supabase
      .from('cxd_projects')
      .update({
        yjs_state: base64,
        updated_at: new Date().toISOString(),
      })
      .eq('id', this.projectId);

    if (error) {
      console.error('[SupabasePersistence] Failed to save Y.Doc state:', error);
    }
  } catch (err) {
    console.error('[SupabasePersistence] Save error:', err);
  } finally {
    this.isSaving = false;
  }
}
```

**Part B: Add a save-on-visibility-hidden flush for yjs_state**

Currently `use-project-sync.ts` flushes JSON `project_data` on `visibilitychange` and `beforeunload`, but `SupabasePersistence` only saves on the 2-second debounce timer. If a user makes a change and immediately closes the tab, the debounced save may never fire.

In `src/lib/yjs/supabase-persistence.ts`:
- Add a public `flush()` method that cancels the debounce timer and saves immediately
- Export this so the context can call it

In `src/contexts/yjs-project-context.tsx`:
- Add a `visibilitychange` listener that calls `supabasePersistenceRef.current.flush()` when the page goes hidden
- Add a `beforeunload` listener that does the same

**Part C: Ensure destroy() does a MERGED save, not a blind overwrite**

The current `destroy()` calls `this.save()` which (after our fix) will do the read-merge-write. Good. But also make sure the `destroyed = true` flag is set AFTER the final save completes (currently it's set before, which causes `save()` to bail out immediately on line 71). Fix: call `save()` first, THEN set `destroyed = true`.

**Important constraints:**
- Do NOT change the Supabase schema or RLS policies — work within the existing `.update().eq('id', projectId)` pattern
- Do NOT change the Y.Doc structure or bridge callbacks
- Keep the debounce interval at 2000ms (don't make it more aggressive — Supabase has rate limits)
- Use `import * as Y from 'yjs'` (already imported)
