In `save()`, after a failed save:
- Increment `consecutiveFailures`
- If `consecutiveFailures >= 5`, call `this.onPersistenceError?.('Save failed 5 times consecutively. Your changes are safe locally but not yet synced to the cloud.')`
- On successful save, reset `consecutiveFailures = 0`

For network errors specifically, schedule a retry:
```typescript
private scheduleRetry(attempt: number): void {
  if (attempt >= 3) return; // max 3 retries
  const delay = Math.pow(2, attempt) * 1000; // 1s, 2s, 4s
  setTimeout(() => this.save(), delay);
}
```

The IndexedDB layer should handle offline persistence correctly. No changes needed to `indexeddb-persistence.ts` unless you find a bug.

**Part B: Verify and fix the load order for stale yjs_state**

In `yjs-project-context.tsx` (around lines 105-128), the load order is:
1. `localPersist.whenSynced()` — loads IndexedDB state into Y.Doc
2. `supabasePersist.load()` — loads yjs_state from Supabase and applies to Y.Doc

Both may be awaited in `Promise.all`. Since Yjs CRDT merge is idempotent and order-independent, applying both should be safe. But verify: if IndexedDB has NEWER state than Supabase (because the user edited offline and Supabase save failed), the merge should preserve the newer edits. This IS how Yjs works — `Y.applyUpdate()` merges, never overwrites.

**If an issue is found, apply the appropriate fix:**

- **If IndexedDB state is being discarded** (e.g., doc is recreated after IndexedDB load): Move the Supabase load to happen AFTER IndexedDB synced, not in parallel. Change from `Promise.all([localPersist.whenSynced(), supabasePersist.load()])` to sequential: `await localPersist.whenSynced(); await supabasePersist.load();`

- **If the doc is replaced instead of merged** (e.g., `Y.applyUpdate` is called with `Y.encodeStateAsUpdate` which replaces rather than merges): This would be a bug in Plan 01-01's `load()` method. The fix is to use `Y.applyUpdate(doc, remoteUpdate)` which always merges, never replaces.

- **If IndexedDB is not being initialized at all** (constructor not called, or called with wrong db name): Fix the constructor call to use the correct project-specific database name.

- **If no issues are found**: Document in a code comment that the load order was audited and confirmed safe: IndexedDB and Supabase states are CRDT-merged, so the union of both is always correct regardless of which is newer.
